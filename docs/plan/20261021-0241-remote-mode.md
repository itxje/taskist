# 20261021-0241-remote-mode Remote mode: one database served to tk on other machines

## Context

- The MVP plan (`20260927-1154-taskist-mvp`) listed "no daemon, no server" and "multi-machine
  sync" as non-goals. Work has since spread over several machines, each with its own
  database (`TASKIST_DB` or the default data directory), and follow-ups recorded on one
  machine are not visible from another. This plan changes that non-goal for one narrow mode:
  remote execution against a single database, not synchronisation.
- `src/main.rs` captures arguments, environment variables, a current-directory reader and the
  terminal state into an `Env` and calls `taskist::run(&args, &env)`, which returns the exit
  code. Every command opens the store, runs one transaction and renders through `src/output.rs`,
  the only module that writes to stdout or stderr (`emit_text`, `emit_success`, `emit`,
  `emit_failure`). The library reads the process environment only through `Env`
  (`TASKIST_DB`, `TASKIST_ACTOR`, `TASKIST_PROJECT`, `TASKIST_FORMAT`, colour variables).
- Commands read local input in two places: a body of `-` (`add`, `edit`) reads stdin, and
  `import FILE|-` reads a file or stdin (`command/exchange.rs`). Project paths given to
  `project add/edit` are made absolute against the current directory (`Env::absolute`), and the
  directory scope matches the current directory against stored project paths (`scope.rs`).
- SQLite runs in WAL mode with a busy timeout; concurrent writer processes are already tested
  (`tests/concurrency.rs`), so concurrent forwarded commands need no extra locking.

## Proposal

Remote execution of the unchanged command code, over one small protocol, with no new
dependency.

1. **Output sink.** `output.rs` writes through a sink instead of the process's stdout and
   stderr: `run` keeps its signature for the binary (sink = the process streams) and gains
   `run_with(args, env, sink)` used by the server, whose sink collects the two byte streams.
   Colour decisions keep coming from `Env` (terminal state and colour variables), so a
   forwarded run renders exactly as the client's terminal would.
2. **Input source.** `Env` gains an optional stdin buffer. A `-` body or `import -` reads it
   when present, else the process stdin as today. The client turns `import FILE` into
   `import -` plus the file's bytes, so the server never opens client paths.
3. **Protocol.** One TCP connection per command. The client sends one JSON line:
   `{"v":1,"token":...,"args":[...],"vars":{...},"cwd":...,"terminal":bool,"stdin":base64|null}`
   where `vars` holds only `TASKIST_ACTOR`, `TASKIST_PROJECT`, `TASKIST_FORMAT`, `NO_COLOR`,
   `CLICOLOR`, `CLICOLOR_FORCE` and `TERM` (never `TASKIST_DB`). The server replies with one
   JSON line `{"v":1,"exit":n,"stdout":base64,"stderr":base64}` and closes. Request and reply
   are bounded (16 MiB), reads and writes have timeouts, and the server handles each connection
   on its own thread up to a fixed limit.
4. **`tk serve --listen ADDR`.** Requires `TASKIST_TOKEN` (refuses to start without it),
   compares tokens in constant time, builds an `Env` from the request (its own `TASKIST_DB`,
   the client's `vars`, `cwd` and terminal state, the stdin buffer) and calls `run_with`.
   Refuses forwarded `serve`. Logs one line per request to stderr (command name, exit code,
   duration), never the token or the bodies.
5. **Client.** When `TASKIST_SERVER=HOST:PORT` is set, `tk` parses the arguments locally
   first (usage errors stay local and identical), runs `guide`, `completions`, `--help` and
   `--version` locally, and forwards every other command; it writes the returned streams and
   exits with the returned code. Two new errors: `unreachable` (connect, timeout or a broken
   reply) and `unauthorized` (token refused), each with its own exit code, rendered like the
   existing errors in text and JSON.
6. **Scope across machines.** The client sends its current directory; directory scope works
   when the machines share project paths (they do: `/workspace/...`). `--project` and
   `TASKIST_PROJECT` work regardless.
7. **Docs and tests.** `docs/guide.md` (variables, `serve`, the two errors),
   `docs/architecture.md` (modules and the protocol), `docs/changelog.md`. Tests: a forwarded
   run equals a local run for every command family in text and JSON; stdin body and
   `import FILE` forwarded; wrong and missing token refused with nothing written; unreachable
   server; `TASKIST_DB` in client vars ignored; oversized request refused; concurrent forwarded
   writers lose nothing.

Deployment after merge (outside this repository): the machine holding the owner's database runs
`tk serve --listen 0.0.0.0:3000` under tmux (container port 3000 is published on the private
network as `100.64.0.6:33000`); other machines set `TASKIST_SERVER=100.64.0.6:33000` and the
token. The existing per-machine databases are merged once with `tk export` / `tk import`.

## Risks

- **No transport encryption.** The protocol is plain TCP with a shared token. It is meant for a
  private network (WireGuard-based tailnet) only; the guide says so, and `serve` refuses to
  start without a token. Exposing it publicly would leak tasks and the token.
- **Output parity.** Any path that writes to stdout or stderr outside `output.rs` would break
  parity; the parity tests guard every command family.
- **Paths.** `project add/edit PATH` stores a path resolved against the client's directory; it
  must mean the same on the server machine, which holds only when paths are shared.
- **Availability.** A client with `TASKIST_SERVER` set cannot work while the server is down; it
  fails with `unreachable` and writes nothing (no local fallback, by design).

## Scope

`src/output.rs`, `src/lib.rs`, `src/env.rs`, `src/cli.rs`, `src/error.rs`,
`src/command/exchange.rs` and `src/command/task.rs` (input source), a new `src/remote.rs`
(protocol, client, server), `src/main.rs`, new `tests/remote.rs`, `docs/guide.md`,
`docs/architecture.md`, `docs/changelog.md`. No dependency added; no schema change.

## Alternatives

- **HTTP with crates (`tiny_http`, `ureq`).** Familiar, but adds dependencies and buys nothing
  for one request type on a private network.
- **SSH as transport (`ssh host tk ...`).** No server code, but needs SSH access between every
  pair of machines and containers, which the current setup does not have.
- **Synchronisation of several databases.** Conflicts, ids and merge rules; much larger and the
  MVP's reason for excluding sync still holds.
- **A shared file system for one SQLite file.** SQLite over network file systems is unsafe for
  concurrent writers.

## Annotations

- 2026-10-21 04:10, implementation: the protocol sends the input as raw bytes after the JSON
  header line (`input_len`), and the reply's `stdout` and `stderr` as JSON strings, since all
  output is UTF-8; no base64. The reply is `{v, ran: {...}}` or `{v, refused: {code, message}}`.
- The client does not rewrite `import FILE` to `import -` (finding the positional in the raw
  arguments is ambiguous); it sends the file's bytes as the input, and a forwarded import reads
  the forwarded input whatever path it names, so the server still never opens client paths.
- `USER` and `CI` are forwarded as well: the actor fallback and the colour rules read them.
- The client sends its canonical current directory and the server uses it as given (a new
  `Env::canonical_current_dir`), because the server cannot resolve another machine's path;
  `src/scope.rs` changed for this.
- `README.md` and `tests/docs.rs` changed too: the two new variables count as unset when
  empty, a fact both documents state.
