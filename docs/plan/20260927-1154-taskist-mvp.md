## Context

- Greenfield: the project directory is empty, no git repository, no existing code.
- Toolchains available locally: Go, Rust (`cargo`), Bun.
- Goal: one central place to record unfinished / follow-up work across many
  projects, grouped by feature inside each project, usable from any terminal
  and drivable by AI agents without special integration.

Existing tools considered:

| Tool | Fit | Gap |
|---|---|---|
| Taskwarrior | Mature, `project:web.auth` hierarchy, JSON export | Large filter grammar that agents get wrong, no directory-to-project mapping, heavy config, v3 storage churn |
| todo.txt | Plain text, trivial | No feature level, no stable IDs (line numbers shift), no concurrency safety |
| beads (`bd`) | Agent-first issue tracker | Per-repository and git-backed, not a central cross-project list |

Conclusion: a small purpose-built CLI is justified if it stays small.

## Proposal

### 1. Product shape

- Single static binary `tk` (project name `taskist`). No daemon, no server, no TUI in the MVP.
- Central store in one SQLite file: `${XDG_DATA_HOME:-~/.local/share}/taskist/taskist.db`,
  overridable with `TASKIST_DB`.
- Hierarchy: **project -> feature -> task**. Feature is optional on a task.

### 2. Data model

```text
project  id, name (unique, [a-z0-9-]), path (nullable, unique), description,
         archived, created_at
feature  id, project_id, name (unique per project), created_at
task     id (global integer, never reused), project_id, feature_id (nullable),
         title, body, status, priority (0-3, default 2), tags (list),
         created_at, updated_at, closed_at, created_by
note     id, task_id, text, author, created_at        -- append-only log
```

Task status set (small and fixed):

| Status | Meaning | Counted as open |
|---|---|---|
| `todo` | Not started / follow-up | yes |
| `doing` | In progress | yes |
| `blocked` | Waiting on something (reason stored as a note) | yes |
| `done` | Finished | no |
| `dropped` | Won't do (reason stored as a note) | no |

Global integer IDs keep commands short (`tk done 42`) and give agents one stable
handle regardless of project.

### 3. Scope resolution (which project a command targets)

In order of precedence:

1. `-p/--project <name>` flag
2. `TASKIST_PROJECT` environment variable
3. Current working directory matched against registered project paths
   (longest prefix wins), so `cd ~/code/web && tk add "..."` just works
4. Otherwise: listing commands show all projects; writing commands fail with a
   usage error that names the missing flag

Projects are created explicitly (`tk project add`) so typos do not create stray
projects. Features are created implicitly on first use of `-f <name>` and can be
renamed or merged later; `tk feature ls` shows what exists so agents can reuse names.

### 4. Command surface

```text
tk project add <name> [--path DIR] [--desc TEXT]
tk project ls | show <name> | edit <name> [...] | archive <name> | rm <name>
tk feature ls [-p P]
tk feature mv <old> <new> [-p P]          # rename or merge into existing

tk add <title> [-p P] [-f F] [--pri 0-3] [--tag T]... [--body TEXT|-]
tk ls [-p P] [-f F] [--status S,..] [--tag T] [--all] [--limit N]
tk show <id>
tk edit <id> [--title] [--body] [--pri] [-f F] [--tag +T|-T]... [-p P]
tk start <id>                              # -> doing
tk block <id> <reason>                     # -> blocked + note
tk done <id> [note]                        # -> done
tk drop <id> <reason>                      # -> dropped + note
tk reopen <id>                             # -> todo
tk note <id> <text>                        # append to the log
tk next [-p P] [-f F]                      # highest-priority open task
tk find <query> [--all]                    # substring search over title/body/notes
tk brief [-p P]                            # compact markdown digest for prompts
tk export [--format json|md]  /  tk import <file.jsonl>
tk guide                                   # agent usage instructions
```

Default `tk ls` shows open tasks for the resolved scope, grouped by feature,
sorted by priority then age:

```text
web  (4 open)
  auth
    #12  P1  doing    Fix token refresh race
    #15  P2  todo     Add SSO login
  api
    #18  P2  blocked  Paginate /orders  (waiting on schema)
  -
    #21  P3  todo     Clean up README
```

Multiple IDs are accepted where it makes sense (`tk done 12 15`).

### 5. AI-agent contract

- `--json` on every command (also `TASKIST_FORMAT=json`). Output shape:
  `{"ok":true,"data":...}` on stdout; `{"ok":false,"error":{"code":"not_found","message":"..."}}`
  on stderr. Field names are stable and documented; additive changes only.
- Exit codes: `0` ok, `1` internal, `2` usage, `3` not found, `4` conflict / invalid transition.
- Never interactive: no prompts, no pager, no editor launch, no color when stdout is not a TTY
  (`NO_COLOR` honored). `--body -` reads the body from stdin.
- Idempotent transitions: `done` on a done task is a no-op success, so retries are safe.
- Attribution: `--by <actor>` or `TASKIST_ACTOR` records who created a task or wrote a note
  (e.g. `alan`, `agent:web-refactor`). Defaults to `$USER`.
- Concurrency: SQLite WAL mode, `busy_timeout`, one transaction per command, so several
  agents and a human can write at the same time.
- Bulk intake: `tk import` accepts JSONL (one task per line, same fields as `tk add`) so an
  agent can dump a batch of follow-ups in one call.
- `tk brief` prints a short markdown digest of open work (grouped by feature, blocked items
  flagged) intended to be pasted into or read by an agent at session start.
- `tk guide` prints a self-contained usage guide that can be referenced from a project's
  `AGENTS.md` or an agent skill, so no agent-specific plugin is required.

### 6. Implementation stack

Rust, following the `/pma-rust` baseline (edition 2024, declared MSRV,
`#![forbid(unsafe_code)]`, workspace deny-warnings lints, no `unwrap`/`expect`/`panic!`
in runtime paths).

- CLI: `clap` v4 derive; shell completions via `clap_complete_command`.
- Storage: `rusqlite` with the `bundled` feature (SQLite compiled in, no system
  library needed). Fully synchronous: no async runtime, since every command is one
  short transaction. Schema migrations embedded and applied on open, tracked with
  `PRAGMA user_version`.
- Serialization: `serde` + `serde_json` for `--json` output and JSONL import.
- Errors: `thiserror` 2.x typed errors in the library code, mapped to exit codes;
  `anyhow` only in `main`.
- Paths: `etcetera` (or `dirs`) for XDG data directory resolution.
- Distribution: `x86_64-unknown-linux-musl` + `+crt-static` static binary with a
  size-tuned `[profile.dist]`.
- Quality gates: fmt, clippy, nextest, doctests, cargo-deny, cargo-shear, typos, MSRV check.
- Exact dependency versions verified at crates.io during implementation.

`libsqlite3-sys` (pulled in by `rusqlite`) is a C dependency. That is a Lock 1
exception the baseline already expects for SQLite (there is no mature pure-Rust
SQLite). It gets a `// JUSTIFICATION:` comment in `Cargo.toml` and a record in
`docs/decisions/`.

Proposed layout (single crate; a CLI this size does not need a multi-crate workspace):

```text
Cargo.toml            # package `taskist`, bin `tk`
src/main.rs           # entry: parse args, open store, dispatch, map errors to exit codes
src/cli.rs            # clap definitions
src/output.rs         # human + JSON rendering (the only module allowed to print)
src/model.rs          # Project, Feature, Task, Note, Status, Priority
src/scope.rs          # project resolution: flag > env > cwd mapping
src/store/mod.rs      # connection setup (WAL, busy_timeout), transactions
src/store/schema.rs   # embedded migrations
src/store/*.rs        # queries per entity
tests/                # integration tests driving the binary (assert_cmd + tempdir DB)
```

### 7. MVP acceptance criteria

1. All commands in section 4 except `import`/`export md` work with human and `--json` output.
2. Scope resolution works via flag, env var, and directory mapping, with tests for precedence.
3. Invalid transitions and unknown IDs return the documented exit codes and JSON errors.
4. Two concurrent writers (parallel `tk add` loops) complete without lost writes or lock errors.
5. `tk guide` output alone is enough for an agent to add, list, update, and close tasks.
6. Unit + integration tests with >= 80% coverage; lint clean.

## Risks

- Scope creep toward a full issue tracker (subtasks, due dates, sync). Mitigation: fixed
  status set and a written non-goals list; new ideas become tasks, not MVP scope.
- Implicit feature creation can fragment names (`auth` vs `login`). Mitigation: `tk feature ls`
  and `tk feature mv` for merging; revisit strict mode if it becomes a problem.
- Directory mapping surprises (nested repos, symlinks). Mitigation: resolve real paths,
  longest-prefix match, and `tk ls` always prints the resolved project name.
- Central SQLite file is not git-friendly. Mitigation: `tk export --format json|md` for
  backups and review; storing tasks inside each repo is an explicit non-goal.
- `libsqlite3-sys` is a bundled C dependency, which conflicts with the pure-Rust default.
  Mitigation: record the exception in `docs/decisions/`, pin it via cargo-deny, and review it
  again once a pure-Rust SQLite is production-ready.
- JSON schema is a public contract once agents depend on it; breaking changes need a version bump.

## Scope

- New repository: roughly 10-15 Rust source files plus integration tests, Rust tooling
  config (`deny.toml`, `rustfmt.toml`, `rust-toolchain.toml`, `.config/nextest.toml`),
  a decision record for the SQLite C dependency, repository hygiene files,
  and docs (`README.md`, agent guide).
- Non-goals for the MVP: TUI, due dates / reminders, subtasks / dependencies between tasks,
  multi-machine sync, web UI, per-repo storage.

## Alternatives

| Decision | Recommended | Alternative | Why not (for now) |
|---|---|---|---|
| Storage | SQLite single file | Markdown / TOML files per project | Human-editable and git-friendly, but concurrent agent writes, ID allocation, and cross-project queries become hard |
| Storage | SQLite single file | Append-only JSONL | Simple writes, but every read replays the log and edits get awkward |
| Language | Rust | Go | Chosen by the user: Rust |
| SQLite binding | `rusqlite` (sync, bundled) | `sqlx` sqlite | Needs an async runtime and gives no benefit for one-shot CLI commands; still links `libsqlite3-sys` |
| Storage engine | SQLite via `rusqlite` | `redb` (pure Rust key-value store) | No C dependency, but no SQL: filtering, grouping, and search all have to be written by hand |
| Storage engine | SQLite via `rusqlite` | `turso` / limbo (pure-Rust SQLite rewrite) | Not yet stable enough for a data store people rely on |
| Build vs reuse | Build `tk` | Wrap Taskwarrior with a thin agent layer | Inherits TW's grammar and config complexity; hierarchy and dir mapping still need custom code |
| Agent integration | CLI + `--json` + `tk guide` | MCP server | Extra process to run and configure; CLI works for any agent with a shell. Can be added later on top of the same store |
