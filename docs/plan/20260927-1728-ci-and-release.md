## Context

- The repository has no remote and no `.github/` directory. The target remote
  `git@github.com:itxje/taskist.git` exists, is public and empty.
- Package `taskist` 0.1.0, binary `tk`, `rust-version = "1.96"`; `rust-toolchain.toml` pins
  channel `1.96.0` (profile minimal, clippy and rustfmt), so runners install the pinned
  toolchain from the file.
- `Cargo.toml` defines `[profile.dist]` (inherits release, `opt-level = "z"`,
  `strip = "symbols"`, `panic = "abort"`, fat LTO from release). It has been configured but no
  cross-target build was part of the MVP.
- `rusqlite` uses the `bundled` feature, so every build compiles SQLite from C source: a musl
  build needs a C compiler that targets musl, not only the Rust target.
- The local quality gate is `cargo fmt --all --check`, `cargo clippy --all-targets
  --all-features --locked`, `cargo nextest run --all-features --locked --no-tests=fail
  --run-ignored all`, `cargo test --doc --locked`, `cargo deny check`, `cargo shear`, `typos`,
  `cargo hack check --rust-version --locked`. Lint policy lives in `Cargo.toml`, so clippy runs
  without `-D warnings`.
- Tests never touch the user's database and open no network connection; the concurrency test
  starts real processes.
- GitHub provides native `ubuntu-24.04` (x86_64) and `ubuntu-24.04-arm` (aarch64) runners for
  public repositories. Latest releases checked on 2026-09-27: `actions/checkout` v7.0.1,
  `Swatinem/rust-cache` v2.9.2, `taiki-e/install-action` v2.87.21,
  `actions/upload-artifact` v7.0.1, `actions/download-artifact` v8.0.1; crates.io:
  cargo-nextest 0.9.146, cargo-deny 0.20.2, cargo-shear 1.14.0, cargo-hack 0.6.45,
  typos-cli 1.50.3.

## Proposal

1. `.github/workflows/ci.yml`, on push to `main` and on pull requests:
   - one job on `ubuntu-24.04`: checkout, `Swatinem/rust-cache`, tools through
     `taiki-e/install-action` (nextest, cargo-deny, cargo-shear, cargo-hack, typos), then the
     gate commands above, unchanged from the local gate;
   - a second job, `musl`, on a matrix of `ubuntu-24.04` / `ubuntu-24.04-arm`: install
     `musl-tools`, add the target, `cargo build --locked --profile dist --target
     <arch>-unknown-linux-musl`, assert the binary is static and `tk --version` runs. This
     catches a broken release build before a tag is pushed.
2. `.github/workflows/release.yml`, on tags `v*`:
   - `check` job: the tag without `v` must equal the `Cargo.toml` version, otherwise fail;
   - `build` job, matrix `x86_64` on `ubuntu-24.04`, `aarch64` on `ubuntu-24.04-arm` (native,
     so each binary is run on its own architecture): the same musl build as above, then
     `tk-<version>-<target>.tar.gz` holding `tk`, `LICENSE` and `README.md`, uploaded as an
     artifact;
   - `publish` job (`contents: write` only here): download both archives, write
     `SHA256SUMS`, create the GitHub release for the tag with `gh release create` (preinstalled
     `gh`, no third-party release action), with generated notes.
   - The musl C compiler is `musl-gcc` from Ubuntu's `musl-tools`, set through
     `CC_<target>`; the Rust musl targets link statically by default.
3. Workflow hygiene: `permissions: contents: read` by default, `contents: write` only on
   `publish`; every third-party action pinned to its full commit SHA with the version in a
   comment; a `concurrency` group that cancels superseded CI runs.
4. README: an "Install a release binary" section (download, verify with `SHA256SUMS`,
   extract, place on `PATH`).
5. After approval and local checks: add the remote as `origin`, push `main`, confirm CI
   passes, then push tag `v0.1.0` to publish the first release.

## Risks

- `musl-gcc` building SQLite: expected to work (the SQLite amalgamation needs only libc), but
  unverified until the first run; the CI `musl` job surfaces it on the first push, before any
  tag.
- musl's allocator is slower under multi-threaded load; `tk` is single-threaded and short-lived,
  so no allocator change.
- Arm runners are free for public repositories only; making the repository private would need
  a different aarch64 build (cross-compilation).
- The first push publishes the whole history, and the tag publishes a release: both are
  public and outward-facing.
- Tool versions installed by `taiki-e/install-action` float unless pinned; the plan pins them to
  the versions above.

## Scope

- New: `.github/workflows/ci.yml`, `.github/workflows/release.yml`.
- Changed: `README.md`, `docs/architecture.md` (a short delivery section), `docs/changelog.md`,
  task and plan records.
- No Rust source, dependency or test change.

## Alternatives

- `cargo-zigbuild` on one x86_64 runner for both targets: no arm runner needed and works for
  private repositories, but adds zig and a third-party build driver, and the aarch64 binary
  could only be smoke-tested under emulation.
- `cross` (Docker images per target): the pma-rust default for many targets; heavier and
  slower for two Linux targets that native runners cover.
- `cargo-dist`: generates the whole release pipeline and installers; more machinery than two
  archives need, and it rewrites workflows on upgrade.
